## 里程碑回顾

### M0: Bootstrap（项目骨架）

**目标：** 建立 monorepo 基础结构，让后续开发有地基。

**交付物：**
- pnpm workspace 配置
- 4 个包：api、super-app、admin-web、domain-types
- 基础 NestJS 应用壳
- 基础 Vue 3 应用壳

**复盘：**
- 正确决策：一开始就用 monorepo，后续类型共享零成本
- 改进空间：可以更早引入 CI，但作品集项目优先级是功能完整性

### M1: Auth + Artist Onboarding（认证与入驻）

**目标：** 实现供给侧冷启动流程：化妆师申请入驻 → 运营审核。

**交付物：**
- Mock 登录（支持客户/化妆师/运营三种角色）
- 化妆师入驻申请表单
- 后台审核台（查看、修改状态、填写备注）
- ArtistApplication 领域模型
- MockSessionStore（内存 session 管理）

**复盘：**
- 正确决策：Mock 登录而非真实 OAuth，让项目零外部依赖
- 正确决策：审核状态机（pending → trial/approved/rejected）覆盖真实业务场景
- 关键学习：DI 模式在 NestJS 中的重要性——MockSessionStore 需要在多个模块间共享

### M2: Customer Booking（客户预约）

**目标：** 实现需求侧核心流程：浏览化妆师 → 选套餐 → 预约。

**交付物：**
- Marketplace 模块（3 位模拟化妆师、6 个服务套餐）
- Booking 领域模型（CreateBookingInput、Booking、BookingStatus）
- 客户预约四步流程页面
- 化妆师浏览卡片（头像、评分、标签、擅长场景）
- 套餐选择（价格、时长、材料政策）
- 预约表单（日期、时间、区域、备注）

**复盘：**
- 正确决策：先做直约模式，不做派单/抢单，降低 MVP 复杂度
- 正确决策：套餐数据写死在 store 中，不做 CRUD，聚焦预约流程验证
- 关键学习：domain-types 包的价值在 M2 充分体现——Booking 类型前后端共享，接口零摩擦

### M3: Dashboard & Interview Prep（看板与面试准备）

**目标：** 完成运营看板、作品集展示页、面试文档，让项目达到面试可用状态。

**交付物：**
- Dashboard API（聚合供给/需求/作品集数据）
- DashboardView 运营看板（MVP 总览、供给侧统计、需求侧统计、验收指标、路线图）
- PortfolioView 作品集展示页（7 个可折叠板块）
- 面试讲解脚本（30s/3min/8min 三个版本）
- 项目复盘文档
- README 更新为面试入口

**复盘：**
- 正确决策：Dashboard 聚合已有数据，不引入新的业务逻辑
- 正确决策：PortfolioView 用折叠面板，面试官可按需展开
- 关键学习：作品集项目的"完成"标准不是功能完整，而是面试官能在 3 分钟内理解项目

## 关键技术决策

### 1. Monorepo + domain-types 共享包

**决策：** 用 pnpm workspace 管理 monorepo，将业务类型抽到 `packages/domain-types`。

**理由：**
- PRD 中的术语（Booking、ArtistApplication、ServiceScene）直接变成 TypeScript 类型
- 前后端接口契约自动对齐，改一处全生效
- 未来接真实后端时，类型定义不变

**效果：** M2 开发时，Booking 类型定义一次，super-app 和 api 同时可用，零接口摩擦。

### 2. Mock 数据 + 内存存储

**决策：** MVP 阶段所有数据用内存 Map 存储，不接数据库。

**理由：**
- 作品集目标是展示产品能力，不是做可上线系统
- 零外部依赖，clone 即可运行
- 测试快，不需要 mock 数据库
- 演示时数据可控

**效果：** 面试官 30 秒内就能启动演示，不需要 Docker、数据库配置。

### 3. NestJS DI 模式

**决策：** 用 NestJS 的依赖注入管理 store 和 service。

**理由：**
- 模块间解耦，store 可以在多个 controller 间共享
- 测试时可以注入 mock 实现
- 符合生产级架构模式

**效果：** DashboardController 注入 ArtistApplicationsStore 和 BookingsStore，聚合数据零耦合。

### 4. Vue 3 Composition API

**决策：** 前端全部使用 Vue 3 `<script setup>` + Composition API。

**理由：**
- 类型推导更好，配合 vue-tsc 做静态检查
- 代码更简洁，逻辑复用更灵活
- 不引入 Pinia/Vuex，用 reactive refs 管理状态，保持简单

**效果：** super-app 的 CustomerBookingView 约 700 行，包含 4 步预约流程，全部用 Composition API 实现。

### 5. Node.js 内置测试框架

**决策：** 用 `node:test` 而非 Jest/Vitest。

**理由：**
- 零依赖，Node.js 原生支持
- 配合 tsx 直接运行 TypeScript 测试
- 38 个测试用例，运行时间 < 250ms

**效果：** 测试零配置，`tsx --test "src/**/*.test.ts"` 即可运行。

## AI 协作复盘

### Vibe Coding 模式

**模式定义：** 人类定义产品方向和业务规则，AI Agent 负责架构设计、代码实现和质量检查。

**实际效果：**
- 3 个里程碑，约 2500 行代码，全部由 AI 实现
- 人类投入主要在：PRD 编写、范围决策、架构审核、功能验收
- AI 投入主要在：代码实现、类型设计、测试编写、文档生成

**优势：**
- 开发速度快：3 个里程碑从零到可演示 MVP
- 代码质量有保障：typecheck + 测试 + 人工验收三层把关
- 决策可回溯：所有决策记录在 docs/，git 留痕

**局限：**
- AI 不理解业务上下文，需要人类明确定义需求边界
- AI 倾向于过度设计，需要人类收敛范围
- AI 生成的代码需要人工审核，尤其是安全相关逻辑

### Agent 角色分工

| 角色 | 职责 | 实际效果 |
|------|------|----------|
| Delivery Lead | 编排里程碑、风险、优先级 | 有效，帮助收敛范围 |
| Product Breakdown | PRD 拆 epic/story | 有效，story 粒度适中 |
| Architecture | 模块边界、数据模型 | 有效，monorepo 结构合理 |
| Implementation | 代码实现 | 高效，2500 行代码质量稳定 |
| QA & Release | 测试、验收 | 有效，38 个测试覆盖核心逻辑 |

## 经验教训

### 做对了的事

1. **早期收束定位**：从商业化平台收束为作品集，砍掉所有外部依赖
2. **Monorepo + 类型共享**：domain-types 包让前后端接口零摩擦
3. **垂直切片交付**：每个里程碑都是可独立验收的完整功能
4. **Mock 数据策略**：零依赖，clone 即跑，面试官体验好
5. **测试先行**：38 个测试覆盖核心逻辑，重构有信心

### 可以改进的事

1. **更早引入 CI**：虽然作品集项目不需要，但 CI 能自动验证 typecheck + test
2. **更细粒度的 story**：有些 story 偏大，可以拆得更小
3. **错误处理更完善**：MVP 阶段错误处理偏简单，生产环境需要加强
4. **国际化**：当前全部中文，如果面向海外面试官需要英文版本
